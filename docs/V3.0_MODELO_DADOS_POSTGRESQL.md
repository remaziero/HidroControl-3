# HIDROCONTROL-3
## V3.0 — Modelo de Dados PostgreSQL

### 1. Objetivo

Este documento define o modelo inicial de dados da fase V3.0 — Processamento Local.

O modelo foi elaborado a partir da auditoria das mensagens MQTT reais recebidas pelo broker Mosquitto privado no Raspberry Pi.

O objetivo é preparar uma estrutura PostgreSQL adequada para:

- persistência de telemetria;
- múltiplos dispositivos AC220;
- histórico por dispositivo;
- consultas por período;
- relatórios;
- dashboards;
- futura API;
- expansão do sistema sem necessidade de criar novas tabelas para cada equipamento.

---

## 2. Arquitetura prevista

Fluxo lógico:

```text
ESP32 AC220
    ↓
HiveMQ Cloud
    ↓ bridge TLS
Mosquitto privado
    ↓
Coletor / Processador local
    ↓
PostgreSQL
    ↓
Consultas / Relatórios / Dashboard / API

O Mosquitto continuará responsável somente pelo transporte MQTT.

A gravação no banco será realizada por um serviço independente de coleta e processamento.

3. Estratégia de armazenamento

O PostgreSQL será executado no Raspberry Pi.

O armazenamento definitivo será realizado no NVMe conectado ao Raspberry Pi.

Essa decisão permite:

reduzir escrita no cartão microSD;
aumentar a capacidade de armazenamento;
melhorar desempenho;
facilitar crescimento do histórico;
preparar o sistema para relatórios e dashboards de longo prazo.
4. Tabelas iniciais

O modelo inicial será composto por duas tabelas principais:

devices
telemetry

A tabela devices armazenará dados cadastrais dos equipamentos.

A tabela telemetry armazenará as mensagens periódicas recebidas dos dispositivos.

5. Tabela devices
5.1 Finalidade

Representar cada equipamento físico ou simulado registrado no sistema.

Exemplos:

ac220-000110
ac220-888334
5.2 Estrutura inicial
CREATE TABLE devices (
    id          BIGSERIAL PRIMARY KEY,
    device_id   VARCHAR(64) NOT NULL UNIQUE,
    descricao   VARCHAR(255),
    ativo       BOOLEAN NOT NULL DEFAULT TRUE,
    created_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
    updated_at  TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
5.3 Campos
id

Chave primária interna.

Tipo:

BIGSERIAL

Será utilizada nos relacionamentos internos do banco.

device_id

Identificador lógico do dispositivo.

Exemplo:

ac220-000110

Características:

obrigatório;
único;
corresponde ao deviceId recebido no JSON MQTT;
também aparece no tópico MQTT.
descricao

Campo opcional para identificação amigável do equipamento.

Exemplos futuros:

Banheiro suíte
Laboratório
Residência principal
Simulador Wokwi
ativo

Indica se o equipamento permanece ativo no sistema.

Tipo:

BOOLEAN

Valor padrão:

TRUE

Permite desativar logicamente um dispositivo sem eliminar seu histórico.

created_at

Data e hora de cadastro do dispositivo.

Gerado automaticamente pelo PostgreSQL.

updated_at

Data e hora da última alteração cadastral.

6. Tabela telemetry
6.1 Finalidade

Armazenar todas as mensagens periódicas de telemetria recebidas dos dispositivos.

Todos os equipamentos compartilharão a mesma tabela.

Não será criada uma tabela separada por AC220.

6.2 Estrutura inicial
CREATE TABLE telemetry (
    id               BIGSERIAL PRIMARY KEY,


    device_id        BIGINT NOT NULL
                     REFERENCES devices(id),


    device_timestamp TIMESTAMPTZ NOT NULL,


    epoch            BIGINT NOT NULL,


    modo             VARCHAR(16) NOT NULL,


    flow_frio        NUMERIC(10,2) NOT NULL,
    flow_quente      NUMERIC(10,2) NOT NULL,


    rele_frio        BOOLEAN NOT NULL,
    rele_quente      BOOLEAN NOT NULL,


    wifi             BOOLEAN NOT NULL,
    mqtt             BOOLEAN NOT NULL,


    received_at      TIMESTAMPTZ NOT NULL DEFAULT NOW()
);
7. Relacionamento entre devices e telemetry

O relacionamento será:

devices
   1
   │
   │
   N
telemetry

Um dispositivo poderá possuir milhões de registros de telemetria.

Cada registro de telemetria pertencerá a exatamente um dispositivo.

O relacionamento será realizado através de:

telemetry.device_id
        ↓
devices.id

O identificador textual, como:

ac220-000110

não será repetido em cada linha de telemetria.

Isso reduz armazenamento e melhora eficiência de índices e relacionamentos.

8. Mapeamento MQTT → PostgreSQL

Mensagem MQTT observada:

{
  "deviceId": "ac220-000110",
  "timestamp": "2026-08-19T11:45:04-03:00",
  "epoch": 1787150704,
  "modo": "MIX",
  "flowFrio": 5.10,
  "flowQuente": 0.00,
  "releFrio": 1,
  "releQuente": 0,
  "wifi": 1,
  "mqtt": 1
}

Mapeamento:

MQTT deviceId     → devices.device_id
MQTT timestamp    → telemetry.device_timestamp
MQTT epoch        → telemetry.epoch
MQTT modo         → telemetry.modo
MQTT flowFrio     → telemetry.flow_frio
MQTT flowQuente   → telemetry.flow_quente
MQTT releFrio     → telemetry.rele_frio
MQTT releQuente   → telemetry.rele_quente
MQTT wifi         → telemetry.wifi
MQTT mqtt         → telemetry.mqtt
Raspberry local   → telemetry.received_at
9. Tipos de dados
device_timestamp

Tipo:

TIMESTAMPTZ

Motivo:

O timestamp transmitido pelo ESP32 já possui offset de fuso horário.

Exemplo:

2026-08-19T11:45:04-03:00
epoch

Tipo:

BIGINT

Será mantido inicialmente mesmo sendo redundante em relação ao timestamp.

Finalidades:

auditoria;
validação temporal;
detecção de mensagens retransmitidas;
comparação com relógio do servidor.
modo

Tipo:

VARCHAR(16)

Não será utilizado ENUM nesta primeira versão.

Valores conhecidos:

NORMAL
DUO
MIX

A utilização de texto evita engessar o banco caso novos modos sejam acrescentados no futuro.

flow_frio e flow_quente

Tipo:

NUMERIC(10,2)

Permite armazenamento decimal explícito das vazões.

rele_frio
rele_quente
wifi
mqtt

Tipo:

BOOLEAN

O coletor converterá:

0 → FALSE
1 → TRUE

antes da inserção no PostgreSQL.

10. received_at

O campo:

received_at

não é enviado pelo ESP32.

Ele será gerado pelo PostgreSQL ou pelo coletor no instante em que a mensagem for processada no Raspberry Pi.

Tipo:

TIMESTAMPTZ

Valor padrão:

DEFAULT NOW()

Esse campo permitirá calcular:

received_at - device_timestamp

e analisar atrasos ao longo da cadeia:

ESP32
→ Wi-Fi
→ Internet
→ HiveMQ
→ Bridge MQTT
→ Mosquitto privado
→ Coletor
→ PostgreSQL
11. Índices iniciais
11.1 Consulta por dispositivo e período
CREATE INDEX idx_telemetry_device_timestamp
ON telemetry (device_id, device_timestamp DESC);

Esse será um dos índices principais do sistema.

Permitirá consultas como:

Histórico do dispositivo X entre data A e data B

e:

Última telemetria do dispositivo X
11.2 Consulta por horário de recebimento
CREATE INDEX idx_telemetry_received_at
ON telemetry (received_at DESC);

Permitirá visualizar rapidamente as últimas mensagens processadas pelo Raspberry Pi.

12. Proteção contra mensagens duplicadas

A bridge MQTT opera com QoS 1.

Nesse nível de QoS existe possibilidade de entrega duplicada.

Por isso será criada uma restrição de unicidade baseada em:

device_id + epoch

Implementação:

CREATE UNIQUE INDEX uq_telemetry_device_epoch
ON telemetry (device_id, epoch);

Assim, o mesmo dispositivo não poderá inserir duas vezes uma telemetria com o mesmo epoch.

O futuro coletor deverá tratar tentativa de duplicidade sem interromper o serviço.

13. Estratégia para múltiplos dispositivos

Novos dispositivos não exigirão alterações estruturais no banco.

Exemplo:

ac220-000110
ac220-888334
ac220-123456
ac220-987654

Todos serão registrados em:

devices

e suas telemetrias serão armazenadas em:

telemetry

Isso permite crescimento do sistema sem proliferação de tabelas.

14. Integridade dos dados

Antes da inserção, o coletor deverá validar:

JSON válido;
dispositivo identificado;
correspondência entre tópico e deviceId;
timestamp válido;
epoch válido;
modo válido;
vazões numéricas;
valores binários válidos;
presença de todos os campos obrigatórios.

O PostgreSQL será responsável por reforçar:

chaves primárias;
unicidade de device_id;
relacionamento entre dispositivo e telemetria;
obrigatoriedade de campos;
proteção contra duplicidade.
15. Primeira estratégia de retenção

Nenhuma exclusão automática será implementada inicialmente.

Todos os dados serão preservados enquanto avaliamos:

volume diário;
volume mensal;
crescimento do banco;
desempenho do NVMe;
necessidades de relatórios.

Posteriormente poderão ser avaliadas estratégias como:

particionamento por período;
agregação histórica;
retenção por idade;
compressão;
tabelas de resumo diário/mensal.

Essas decisões não serão antecipadas nesta fase.

16. Volume estimado inicial

Com publicação aproximada a cada:

5 segundos

cada dispositivo gera aproximadamente:

12 mensagens por minuto
720 mensagens por hora
17.280 mensagens por dia

Com dois dispositivos:

34.560 registros por dia

Esse volume é plenamente compatível com PostgreSQL e armazenamento NVMe.

A medição real será feita após a ativação do coletor.

17. Possíveis tabelas futuras

Não serão criadas agora, mas o projeto poderá futuramente incluir:

events
alarms
commands
daily_summary
monthly_summary
device_status
system_logs

O modelo inicial permanecerá propositalmente simples.

18. Decisões consolidadas

Ficam estabelecidas para a primeira implementação da V3.0:

PostgreSQL como banco relacional local.
Banco executado no Raspberry Pi.
Dados armazenados no NVMe.
Uma única tabela telemetry para todos os dispositivos.
Cadastro separado em devices.
Relação por chave numérica interna.
Timestamp com timezone.
Epoch preservado.
Estados binários armazenados como BOOLEAN.
modo armazenado inicialmente como VARCHAR.
Índice por dispositivo e timestamp.
Índice por horário de recebimento.
Proteção contra duplicidade por dispositivo + epoch.
Mosquitto separado da camada de persistência.
Coletor responsável por validação e normalização.
