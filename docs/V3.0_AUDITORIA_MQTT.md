# HIDROCONTROL-3
## V3.0 — Auditoria das Mensagens MQTT Reais

### 1. Objetivo

Este documento registra a auditoria inicial das mensagens MQTT reais recebidas pelo broker Mosquitto privado do Raspberry Pi, marcando o início da fase V3.0 — Processamento Local.

O objetivo desta auditoria é identificar:

- tópicos MQTT efetivamente utilizados;
- estrutura real dos payloads JSON;
- frequência aproximada das publicações;
- tipos de dados recebidos;
- consistência entre tópico e payload;
- campos relevantes para persistência futura em banco de dados;
- premissas para construção do modelo de dados PostgreSQL.

---

### 2. Arquitetura observada

Fluxo atualmente validado:

ESP32 AC220  
↓  
HiveMQ Cloud  
↓ Bridge MQTT TLS  
Mosquitto privado no Raspberry Pi  
↓  
Cliente MQTT local  
↓  
Futura camada de processamento local  
↓  
PostgreSQL

---

### 3. Broker privado utilizado na auditoria

Broker local:

- Host: `127.0.0.1`
- Porta: `1884`
- Autenticação: usuário e senha
- Protocolo: MQTT
- QoS observado no subscribe: `1`

Comando utilizado para auditoria:

```bash
mosquitto_sub \
  -h 127.0.0.1 \
  -p 1884 \
  -u hidrocontrol-admin \
  -P '<SENHA>' \
  -t 'hidrocontrol/+/telemetry' \
  -q 1 \
  -v

4. Dispositivos observados

Durante a auditoria foram observados pelo menos dois dispositivos AC220:

ac220-000110
ac220-888334

Cada dispositivo utiliza seu próprio tópico de telemetria.

5. Tópicos MQTT observados

Foram recebidas mensagens nos seguintes tópicos:

hidrocontrol/ac220-000110/telemetry
hidrocontrol/ac220-888334/telemetry

Estrutura geral:

hidrocontrol/<deviceId>/telemetry

Essa estrutura permite identificar diretamente o dispositivo de origem pela própria hierarquia do tópico.

6. Estrutura real do payload JSON

Exemplo observado:

{
  "deviceId": "ac220-000110",
  "timestamp": "2026-08-19T11:45:04-03:00",
  "epoch": 1787150704,
  "modo": "MIX",
  "flowFrio": 5.10,
  "flowQuente": 0.00,
  "releFrio": 1,
  "releQuente": 0,
  "wifi": 1,
  "mqtt": 1
}

Outro dispositivo apresentou a mesma estrutura de campos, variando apenas os valores.

7. Campos observados
7.1 deviceId

Exemplo:

ac220-000110

Tipo lógico:

string

Função:

identifica unicamente o dispositivo;
também aparece embutido no tópico MQTT;
poderá ser usado como chave de relacionamento com a futura tabela de dispositivos.
7.2 timestamp

Exemplo:

2026-08-19T11:45:04-03:00

Tipo lógico:

datetime com timezone

Características:

formato ISO 8601;
inclui data;
inclui hora;
inclui offset de fuso horário;
permite conversão direta para TIMESTAMPTZ no PostgreSQL.
7.3 epoch

Exemplo:

1787150704

Tipo lógico:

inteiro

Função:

representação Unix Epoch do instante da medição;
redundante em relação ao campo timestamp;
será preservado inicialmente para auditoria e validação temporal.
7.4 modo

Exemplos observados:

MIX
NORMAL

Tipo lógico:

string categórica

Possíveis valores previstos no projeto:

NORMAL
DUO
MIX

Esse campo representa o modo operacional vigente no dispositivo no instante da telemetria.

7.5 flowFrio

Exemplos:

0.00
4.95
5.10

Tipo lógico:

decimal

Representa a vazão medida no circuito de água fria.

7.6 flowQuente

Exemplo:

0.00

Tipo lógico:

decimal

Representa a vazão medida no circuito de água quente.

7.7 releFrio

Valores observados:

0
1

Tipo lógico:

binário

Representa o estado do relé associado ao circuito de água fria.

7.8 releQuente

Valores observados:

0
1

Tipo lógico:

binário

Representa o estado do relé associado ao circuito de água quente.

7.9 wifi

Valores observados:

1

Tipo lógico:

binário

Representa o estado da conectividade Wi-Fi no instante da publicação.

7.10 mqtt

Valores observados:

1

Tipo lógico:

binário

Representa o estado da conectividade MQTT no instante da publicação.

9. Consistência entre tópico e payload

Existe redundância proposital entre:

tópico:
hidrocontrol/ac220-000110/telemetry

e:

"deviceId": "ac220-000110"

Essa redundância é útil e deverá ser aproveitada pelo coletor local.

O futuro coletor MQTT deverá validar:

deviceId extraído do tópico == deviceId presente no JSON

Se houver divergência, a mensagem deverá ser considerada inconsistente e poderá ser:

rejeitada;
registrada em log;
armazenada em uma área de erros para posterior análise.
10. Validações recomendadas no coletor local

Antes de qualquer inserção no banco de dados, o coletor deverá verificar:

JSON válido;
presença de deviceId;
presença de timestamp;
presença de epoch;
presença de modo;
presença de flowFrio;
presença de flowQuente;
presença de releFrio;
presença de releQuente;
presença de wifi;
presença de mqtt;
correspondência entre deviceId e tópico;
tipo correto de cada campo;
valores binários limitados a 0 ou 1;
modo pertencente ao conjunto de valores aceitos;
timestamp válido;
coerência básica entre timestamp e epoch.
11. Diretriz inicial para modelagem de dados

A auditoria indica que não deve existir uma tabela de telemetria por dispositivo.

A abordagem recomendada é:

Tabela de dispositivos

Responsável por armazenar informações permanentes ou cadastrais de cada equipamento.

Exemplo conceitual:

devices
Tabela de telemetria

Responsável por armazenar todas as medições recebidas.

Exemplo conceitual:

telemetry

Cada registro de telemetria deverá possuir referência ao dispositivo de origem.

Essa arquitetura permite adicionar novos dispositivos sem necessidade de criar novas tabelas.

12. Campos candidatos à persistência

Campos mínimos candidatos para a futura tabela de telemetria:

id
device_id
timestamp
epoch
modo
flow_frio
flow_quente
rele_frio
rele_quente
wifi
mqtt
received_at

O campo received_at não vem do ESP32.

Ele deverá ser gerado no Raspberry Pi no instante em que a mensagem for recebida e processada.

Isso permitirá medir:

atraso entre geração e recebimento;
atrasos de bridge;
atraso de Internet;
problemas de sincronismo temporal;
mensagens antigas ou retransmitidas.
13. Campo received_at

Exemplo conceitual:

received_at = horário do servidor Raspberry Pi

Comparação futura:

received_at - timestamp

Essa diferença poderá ser utilizada para diagnóstico da cadeia:

ESP32
→ Internet
→ HiveMQ
→ Bridge MQTT
→ Raspberry Pi
→ coletor local
14. Decisões iniciais da V3.0

A partir desta auditoria ficam estabelecidas as seguintes decisões:

O PostgreSQL será inicialmente executado no Raspberry Pi.
O armazenamento físico poderá ser migrado futuramente para SSD conectado ao Raspberry Pi.
A modelagem será independente do número de dispositivos.
O Mosquitto continuará responsável apenas pelo transporte MQTT.
A persistência será realizada por um serviço separado de coleta e processamento.
O serviço coletor deverá assinar os tópicos locais do Mosquitto privado.
O coletor será responsável por:
validar mensagens;
normalizar dados;
registrar erros;
persistir telemetria;
futuramente gerar eventos derivados.
Os dados recebidos serão tratados localmente no Raspberry Pi.
